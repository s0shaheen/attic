# Task 3.3: Lambda: APIFY_ENRICH

## 0) Outcome

Lambda function `attic-apify-enrich` fetches TikTok video metadata via Apify Clockworks Data Extractor, detecting media type (video/image/slideshow) and populating metadata fields in `media_events`.

## 1) Scope

### In-scope
- [ ] Lambda function that calls Apify Clockworks TikTok Data Extractor
- [ ] Batch processing (50 URLs per Apify call for efficiency)
- [ ] Extract all metadata fields: caption, hashtags, creator info, engagement metrics
- [ ] Detect media type from Apify response (is_slideshow, image_count)
- [ ] Update media_events with enrichment data
- [ ] Track per-item cost in processing_steps table
- [ ] Handle Apify rate limits and errors gracefully
- [ ] Return enriched media_event IDs for next pipeline step

### Out-of-scope / Non-goals
- Media file download (task 3.4)
- Subtitle extraction (task 3.5)
- Transcription (task 3.6)

## 2) System context

### Components touched
- **Lambda function**: `attic-apify-enrich`
- **Third party**: Apify Clockworks TikTok Data Extractor
- **DB tables**: `media_events`, `processing_steps`
- **Step Functions**: Invoked as Map state (batched)

### Invariants (must always be true)
- Apify API key never logged or exposed
- All updates use upserts (idempotent)
- Failed items don't block successful ones
- Cost tracked per item in processing_steps

## 5) Workflow & state machine (if applicable)

### States
- This Lambda IS a state in the pipeline (EnrichBatch Map state)
- Receives batches of up to 50 media items

### Idempotency strategy
- Deterministic processing_step IDs
- Upsert operations for media_events updates
- Apify calls are inherently idempotent (same URLs return same data)

### Failure modes + user-facing behavior
- **Apify rate limit**: Retry with exponential backoff
- **Video not found**: Mark as failed, continue processing others
- **Apify API error**: Retry with backoff, then mark batch as failed
- **Partial batch failure**: Return successful items, log failures
